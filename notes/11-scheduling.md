# Занятие 11. Запуск по расписанию: cron и таймеры systemd

## Главное своими словами
Задания на сервере должны выполняться сами: проверки, бэкапы, отчёты. Для этого есть cron (одна строка, есть везде) и таймеры systemd (два файла, вывод в журнале, пропущенный запуск не теряется, ошибки видны в --failed).

## cron
- Формат: минута час день месяц день_недели команда
- crontab -e / -l; системные задания в /etc/cron.*
- Полные пути, вывод в журнал или файл — иначе ошибки теряются (No MTA installed)

## Таймеры systemd
- Пара: служба oneshot без [Install] + таймер с OnCalendar и [Install] WantedBy=timers.target
- Включается таймер: enable --now имя.timer; start без enable не переживёт перезагрузку
- Persistent=true — для бэкапов; для частых проверок не нужен
- systemd-analyze calendar — проверка расписания; list-timers — обзор
- User=имя, если нужны файлы пользователя; иначе DynamicUser=yes

## Мониторинг
- Точность = интервал проверки
- Проверку нужно испытать на значении, при котором она обязана сработать

## Что я сделал на практике
- **Скрипт check_site.sh.** Проверяет сайт по коду ответа и пишет результат в журнал через logger. Добавил `|| true` после curl: без него при неработающем сайте set -e остановил бы скрипт, и запись об ошибке не появилась бы. При остановленном webdemo в журнал записалось «Fail: ответил 000», код возврата 1.
- **cron.** Поставил проверку каждую минуту. Остановил сайт и по журналу (`journalctl -t check_site`) восстановил время аварии: проверки падали с 15:36 по 15:40. Точность — ±1 минута, как интервал проверки. Строка без полного пути не сработала: cron не нашёл скрипт, а ошибка потерялась — в журнале осталось только «No MTA installed, discarding output».
- **check-disk.timer.** Перенёс проверку дисков на таймер каждые 5 минут, от DynamicUser, скрипт скопировал в /usr/local/bin. Чтобы проверить срабатывание, временно поставил порог 80: служба стала failed и появилась в --failed (диски E: и F: заполнены на 84% и 83%). Вернул 90 — служба снова inactive после выполнения. Перезапуск не понадобился: каждый запуск oneshot — новый процесс.
- **Перенос check_site из cron в таймер.** Вместо `cp` случайно запустил скрипт, передав ему путь как URL: в журнале появилось «Fail: /usr/local/bin/check_site.sh ответил 000», а служба падала с 203/EXEC. Нашёл по коду ошибки и строке журнала, скопировал файл. После этого проверка поймала учебную остановку сайта. Строку из crontab удалил.
- **Ежедневный бэкап.** backup.sh запускается в 03:00 от пользователя vetal, потому что ему нужны мои файлы в /home/vetal. Ручной запуск создал архивы с сегодняшней датой, ротация удалила три архива старше 7 дней.
- **Ошибки с включением.** Таймеры check-site и backup запустил через start, но не через enable — после перезагрузки они бы не заработали. Плюс добавил [Install] в службу бэкапа вместо Persistent=true в таймер. Исправил: служба без [Install] (static), в таймере Persistent=true, все таймеры enabled.

## Что стало открытием
- Ошибки cron теряются молча, а таймер systemd пишет всё в журнал
- Точность мониторинга равна интервалу проверки
- start без enable выглядит рабочим, но не переживает перезагрузку — та же разница active и enabled
- Сама система уже работает на таймерах: logrotate, apt-daily, dpkg-db-backup
- Ротация бэкапов в боевых условиях удаляет реальные старые копии — это надо помнить
