# Занятие 3. Пользователи, группы и права доступа

## Главное своими словами
Пользователи и права в Linux нужны для того, чтобы каждому пользователю выдать ровно столько прав, сколько ему достаточно для работы. Это принцип минимальных привилегий: если сайт взломают, взломщик получит только права пользователя сайта (например, www-data), а не всю систему.

## Пользователи
- Где хранятся: `/etc/passwd`
- Формат строки /etc/passwd: `логин : пароль : UID : GID : комментарий : домашняя папка : оболочка (shell)`. Вместо пароля стоит `x` — сам пароль хранится в другом месте
- UID 0 — root, UID < 1000 — системные (служебные) пользователи, UID ≥ 1000 — люди
- nologin — под этим пользователем нельзя зайти в терминал. Так делают у служебных пользователей
- Где пароли и почему закрыты: в `/etc/shadow` хранятся хэши паролей. Читать может только root, потому что по хэшу можно попробовать подобрать пароль

## Группы
- Зачем: чтобы выдавать права сразу нескольким пользователям (как ключ, который выдают целому отделу)
- Основная и дополнительные: основная обычно совпадает с именем пользователя, это его личная группа. Дополнительные дают дополнительные права, например группа `sudo` даёт право пользоваться sudo
- Добавить в группу: `sudo usermod -aG группа пользователь` — почему именно так: `-a` добавляет группу к уже существующим. Без `-a` пользователь потеряет все остальные группы, включая sudo
- Когда применяется: только после нового входа в систему (`su - имя` или новое SSH-подключение). Текущая сессия новую группу не видит

## Права доступа
- Строка прав: тип (`-` файл, `d` папка, `l` ссылка) + `rwx` владелец + `rwx` группа + `rwx` все остальные
- Порядок проверки: владелец → группа → остальные. Срабатывает только ОДНА тройка — первая подходящая. Сначала определяю свою тройку, потом смотрю буквы
- r, w, x для файла: читать, изменять, запускать как программу
- r, w, x для папки: видеть список имён, создавать/удалять/переименовывать файлы внутри, заходить в папку. Права папки НЕ наследуются файлами — папка работает как дверь
- Цифры: r=4, w=2, x=1; 644 — `rw-r--r--`, 600 — `rw-------`, 755 — `rwxr-xr-x`, 700 — `rwx------`
- root и права: root игнорирует проверку прав — может читать и менять любые файлы. Поэтому под root постоянно не работаю, только sudo для конкретной команды

## Изменение прав
- chmod буквами: `chmod u+x файл` — добавить владельцу право на запуск
- chmod цифрами: `chmod 700 файл` — закрыть доступ всем, кроме владельца (и root)
- chown / chgrp: `sudo chown www-data:www-data hello.sh` — сменить владельца и группу; `sudo chgrp webteam файл` — сменить только группу. Выполнить может только root, иначе любой мог бы присвоить чужой файл
- Никогда не делаю: `chmod 777` («чтобы заработало»); `usermod -G` без `-a`; не оставляю секреты с правами 644

## Особые биты
- sticky bit (t): в общей папке создавать файлы могут все, но удалять и переименовывать — только свои. Пример: `/tmp`. Аналогия — общий холодильник: положить может каждый, забрать — только своё
- setgid (s): специальный бит на папке. С ним все новые файлы внутри автоматически получают группу папки, а не группу создателя
- Как не путать: `t` — «кто может удалить», `s` — «какую группу получит новый файл»

## Что я сделал на практике
- **Скрипт hello.sh.** Создал скрипт, `./hello.sh` выдал Permission denied. `ls -l` показал `-rw-r--r--` — нет права `x` (новые файлы создаются без него). Решение: `chmod u+x hello.sh` → `-rwxr--r--`, скрипт запустился. Потом отдал файл www-data (`sudo chown`) — снова не запускался: для меня стала действовать тройка «остальные» `r--`.

- **Секретный файл.** Создал `secret.txt` с учебным паролем. `ls -l` показал права `-rw-r--r--` (644): новые файлы по умолчанию может читать ЛЮБОЙ пользователь системы. Закрыл файл командой `chmod 600 secret.txt` → стало `-rw-------`: читать и изменять может только владелец (и root, который игнорирует права). Вывод: файлы с паролями, ключами, токенами (например, `.env`) нужно закрывать сразу после создания — сами по себе они не защищены.

- **Общая папка для группы.** Задача: две учётные записи (vetal и testuser) должны работать в одной папке, а остальные — ничего не видеть. Создал группу `webteam`, добавил в неё обоих (`usermod -aG`), создал `/srv/webteam` с владельцем `root:webteam` и правами `770`.
  - Проблема 1: после добавления в группу у vetal всё равно не было доступа. Причина — группы загружаются при входе в систему. Решение: перезайти (`su - vetal`).
  - Проблема 2: vetal не мог дописать в файл, созданный testuser. `ls -l` показал, что файл получил группу создателя (`testuser`), а не группу папки → для vetal действовала третья тройка `r--`. Решение: включил на папке setgid (`chmod g+s`) — новые файлы стали получать группу `webteam`; старый файл исправил через `chgrp webteam`.
  - В конце удалил учебного пользователя, группу и папку.
  - Вывод: для совместной работы права выдают через группу; для общих папок нужен setgid; после изменения групп нужен перевход.

## Что стало открытием
- Насколько сложно и интересно устроены права и доступы и насколько разнообразно их можно выдавать и забирать.
- Права папки и права файла — разные вещи: удалить файл можно и без прав на сам файл, если есть `w` на папку.
- Каждый sudo записывается в `/var/log/auth.log` — всегда видно, кто и что делал.
